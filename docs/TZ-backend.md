Документ описывает поведение, данные и контракты. Стек сервера MVP — NestJS. Хранилище продукта — Neon, serverless Postgres. Это решение реализации, не новое правило проверок. Подключение берётся из окружения, не из кода и не из отчёта. Схему таблиц этот документ не задаёт.

В Neon кладутся данные, которые уже должны переживать процесс: пользователи, которых создал ТЛ (логин, хеш пароля, роль), кэш каталога, отчёты (3 месяца), админ-конфиг, учёт затрат, если он хранится. Распакованные каталоги лендов и zip в Postgres не класть: в этом ТЗ это файлы. Место файлов стенда по-прежнему не задано. Токен AIO в базу не писать. Учётку `TL_LOGIN` / `TL_PASSWORD` в базу не копировать. Других полей учётки, кроме логина, хеша пароля и роли, не добавлять.

Внутренний HTTP API помощника в исходном ТЗ отсутствует. Раздел «Предлагаемый контракт MVP» выведен из сценариев, чтобы сойтись с frontend. Это не новое бизнес-правило. Имена маршрутов исходным ТЗ не зафиксированы.

Секреты и образцы в репозиторий, отчёт и логи не писать: значение `AIO_TOKEN`, `TL_LOGIN`, `TL_PASSWORD`, пароли пользователей, подписанные URL, живые URL `preview_image`.

## Назначение MVP

Внутренний инструмент до 10 человек. Пользователь выбирает ленд в каталоге или вводит `human_id`. Система скачивает `original`, гоняет статику, поднимает изолированный просмотр, вызывает ИИ и Lighthouse, показывает отчёт.

Отчёт рекомендательный. Общего вердикта «годен / не годен» нет. Сервис такой вердикт не вычисляет и не отдаёт.

Цель 2–3 минуты от ввода `human_id` до отчёта — цель. Она не повод убрать пункты статики.

## Роли

Создавать пользователей может только ТЛ. QA методы пользователей не видит и не вызывает. Саморегистрации нет. Это не учётные записи AIO и не `AIO_TOKEN`.

Первый ТЛ не создаётся через интерфейс. Логин и пароль — `TL_LOGIN` и `TL_PASSWORD` в окружении. Значения в репозиторий, отчёт и логи не писать. Пароль из `TL_PASSWORD` в базу не копировать.

Остальных пользователей создаёт ТЛ. У создаваемого: логин, пароль, роль ТЛ или QA. Запись в Neon. В базе пароль только как хеш, не открытым текстом. Поля записи — логин, хеш пароля и роль. Других полей учётки не добавлять.

Вход: `POST /session`, тело `{ "login", "password" }`. Сначала сравнение пары с `TL_LOGIN` и `TL_PASSWORD`. Совпала пара — роль ТЛ. Иначе пользователи из Neon. Чужой логин или пароль — отказ входа, без уточнения, какое из двух неверно. Восстановления пароля и самостоятельной смены пароля в MVP нет.

| Роль | Поведение сервиса |
|------|-------------------|
| ТЛ | Запуск всех проверок. Все отчёты. Статистика затрат, если провайдер вернул учёт. Чтение и запись админ-конфига. Создание пользователей. Список пользователей: логин и роль, без пароля и без хеша |
| QA | Запуск полного набора проверок. Только свои отчёты. Затраты не отдавать, в том числе через API. Конфиг не читать и не менять. `GET /admin/users` и `POST /admin/users` — отказ |

## Что не входит в MVP

- Общий статус проверки и автоматический блок ленда.
- Отдельный логин каждого QA в AIO. Один сервисный токен.
- Анализ архива `merged`.
- Исходящие интеграции: Jira, Telegram, почта, таблицы.
- Отдельное скрытие персональных данных на ленде.
- История изменений админ-конфига.
- Фиксированный суточный объём проверок.
- Золотой набор эталонных лендов.
- Саморегистрация.
- Восстановление пароля и самостоятельная смена пароля.
- Удаление и редактирование пользователей.

## Авторизация AIO

Один сервисный токен в окружении: `AIO_TOKEN`.

На URL каждого вызова AIO из этого ТЗ ставится query-параметр `token`. Вызовы: список лендов, `POST /api/v1/actions/process`, опрос уведомлений, скачивание файла по URL из уведомления.

Cookie нет. Заголовка `Authorization` нет. Заголовка `x-tenant-id` нет.

Значение токена не писать в репозиторий, отчёт, логи и ответы внутреннего API.

## Каталог последних 300

Система хранит последние 300 лендов. Сортировка запроса в AIO — сначала новые. Фон обновляет кэш каждые 10 минут. Кнопка «Обновить» обновляет список сразу, тем же запросом. Опрос раз в 10 минут только наполняет кэш, чтобы ввод `human_id` не ждал сеть.

Запуск без `uuid` сравнивает `human_id` как точную строку. Пример: `359226`. Поле лежит только в `_identity.human_id`. На верхнем уровне строки его нет.

Если `human_id` нет в кэше, список обновляется один раз, затем поиск повторяется. Если после этого записи нет, проверка останавливается. Скачивание не начинается.

Если несколько строк с одним `human_id` и в запуске нет `uuid`, выбор не делается. Проверка останавливается, наружу уходит коллизия.

Экран запуска читает тот же кэш. Ответ списка для экрана уже отсортирован по убыванию числового `human_id` (больший id сверху), не лексикографически. Запрос в AIO из-за этой сортировки не меняется: там по-прежнему сначала новые.

`created_at` для этого списка — верхнее поле строки. `_identity.created_at` не читать. Нет верхнего `created_at` — в элементе списка поле пустое, строку не выбрасывать. `uuid` в этом ответе есть: он нужен клиенту для запуска выбранной строки, не для колонки таблицы.

Запуск текстом передаёт только `human_id`. Запуск выбранной строки передаёт `human_id` и `uuid` этой строки. Если `uuid` передан, берётся строка кэша с этой парой, даже когда тот же `human_id` встречается ещё раз. Пара не совпала ни с одной строкой — ошибка, скачивание не начинается.

Обязательны `uuid` и `human_id`. Строку без них в каталог не класть. Нет другого поля — сохранить пустым и идти дальше. Отдельного пользовательского текста на пустое необязательное поле нет.

Метрики в кэш ленда не складывать.

### 4.1 Запрос списка

`POST https://app.aio.tech/api/v1/tables/data`  
`Content-Type: application/json`  
Авторизация — query-параметр `token`.

Ключ таблицы — строка `Funnel\Landers`. В JSON один обратный слэш, в примере ниже он экранирован.

Остальные поля тела остаются как в захвате. Идентификаторы метрик на поиск не влияют: в тело кладётся заглушка, не живые uuid метрик из снимка.

Карточка читается из `_identity`. Верхний `uuid` строки в захвате совпадает с `_identity.uuid`.

Поля карточки до скачивания:

| Поле | Зачем |
|------|--------|
| `uuid` | Аргумент скачивания и сопоставление уведомления |
| `human_id` | Ключ отчётов и сравнения |

| `mvt_settings` | Строка с JSON, не объект. Контекст вариантов. В правила статики не превращать |

Текст оффера из примера в правила не входит.

## Скачивание

Скачивание в AIO по-прежнему идёт по `uuid` строки кэша. Человек этот `uuid` не набирает: его приносит выбор строки вместе с `human_id` либо сервер берёт единственную строку точного `human_id`.

`POST https://app.aio.tech/api/v1/actions/process`  
`multipart/form-data`:

| Поле | Значение |
|------|----------|
| `action` | `Lander\Download` |
| `repository` | `Eloquent\LanderRepository` |
| `arguments[is_archived]` | `true` |
| `uuids[0]` | `uuid` ленда |

Ответ `200`: `messages[].message` = `Download Requested`; `primary` и `uuid` повторяют `uuid` ленда. Файла в этом ответе нет. Этот ответ отчётом не считается.

Затем `GET https://app.aio.tech/api/v1/notifications?limit=25&page=1&unread_only=false`.

Искать элемент с `notification.type` = `lander.download`, у которого `payload.lander_uuid` равен запрошенному `uuid` и `payload.status` = `done`.

В `payload` также есть `human_id`, `lander_name`, `lander_uuid`, `link_ttl_days`. В наблюдаемом ответе срок ссылки 7 дней. Это наблюдение, не правило хранить образец ссылки. `payload.files[]`:

| `kind` | `label` | Смысл |
|--------|---------|--------|
| `merged` | Merged export | Ленд с текущими изменениями AIO. Не скачивать |
| `original` | Original upload | Архив, которым ленд когда-то загрузили. Берём только его |

Из `payload.files[]` выбрать `kind=original`. `merged` не скачивать и не проверять.

Если макросы `{{form}}`, `{{cdn}}/` и защита трекера есть только в merged, статика может дать `failed`. Это ожидаемо. К merged не возвращаться.

Дальше файл берётся по URL из уведомления. URL подписанный и ограничен по времени. Образцы URL не хранить. Ссылка не является результатом проверки. Во внутренний API и в постоянный отчёт этот URL не класть.

Интервал опроса уведомлений и граница одной попытки до повтора исходным ТЗ не заданы. См. открытые вопросы.

Ожидаемая основа архива: в корне `index.html` или `index.php`, каталоги `css`, `js`, `images`. Типы preland, land и offer этой раскладке соответствуют. Отличие типов — наличие формы, а не другая раскладка папок. Правила структуры задаёт проверка SpyOwl, не список папок образца. Верхний уровень образца в исходном ТЗ: `index.html`, `favicon.ico`, `css/`, `js/`, `images/`, `fonts/`. Имя файла образца и живые URL сюда не копировать.

## Распаковка и каталоги

Одновременно у пользователя один развёрнутый ленд. Пользователи друг друга не вытесняют.

- Новый запуск того же пользователя удаляет его предыдущий распакованный каталог до развёртывания нового.
- После полного создания отчёта каталог можно удалить.
- Отчёты не удаляются вместе с каталогом.
- Запись отчёта хранится 3 месяца.

Стартовые значения равны коду на дату чтения, как они записаны в таблице ниже.

Критичная находка — `failed`. Она останавливает автоматический переход к ИИ. `warning` переход не останавливает.

Если структура `failed`, остальные статические пункты не запускаются. В отчёте их нет, а не статус `failed` без прогона. После успешной структуры остальные пункты можно считать параллельно.

`expectFormMacro` в админ-конфиге стартует как `true`. В файлах конфига aio-checker поле равно `true`. Если файла нет, код aio-checker считает `false`. Для MVP в конфиг кладём `true`. Автоматически выводить флаг из `lander_type.name` нельзя: таблица соответствия не задана.

## Стенд

Стенд нужен, чтобы человек и ИИ видели ленд с подставленными макросами. Пользователь получает временный URL, если окружение умеет его выдать.

Подстановка при отдаче страницы — как у Compilator, `vendor/compilator/server.mjs`:

| Макрос | Чем заменяется |
|--------|----------------|
| `{{form}}` | HTML из конфига стенда `form.html` |
| `{{aio.visit.fields.offer_name.for_visitors}}` | Строка `brand_name` из конфига стенда `config.json` |
| `{{cdn}}` | База CDN стенда. В страницу также передаётся `window.__CDN_BASE__` |

Другие макросы этот просмотр не подставляет. Пайплайн `src/steps/04-macros.js` заменяет только `{КЛЮЧ}` из `macros.conf` и к просмотру AIO-ленда не относится. Значения из `macros.conf` в продукт не переносить.

Содержимое `form.html`, строка `brand_name` и конкретная база CDN исходным ТЗ не заданы.

Пока QA явно не разрешил действия ленда, развёрнутая копия сама ничего не выполняет: нет отправки лидов и нет срабатывания сторонних пикселей. Разрешение — явное действие на этом просмотре, не молчаливое включение. В тексте исходного ТЗ действие названо действием QA. Может ли ТЛ дать то же разрешение на своём просмотре, не задано.

Ориентир изоляции: `src/config/defaults/blacklist.json` со свойствами `removeAllExternalScripts`, `defaultDenyExternalScripts` и пустыми allow-списками. Этот файл — список доменов и паттернов, которые пайплайн SpyOwl вырезает при очистке, а не отчёт aio-checker. Пункты файла отдельными проверками статики не делать. Сами домены и паттерны файла в это ТЗ не копировать: в исходном ТЗ они не перечислены.

Временный URL, если он подписанный, в постоянный отчёт не класть.

Ветка «человек не разрешил ИИ»: раздел 7 запрещает автостарт только ИИ. Пункт 7 раздела 3 ставит стенд и ИИ в одну ветку «критичных нет, либо пользователь разрешил продолжить». Поднимать ли стенд и Lighthouse после отказа — открытый вопрос. До закрытия не включать их молча в момент отказа.

## ИИ

Модель: Qwen, быстрый вариант. Ограничения компании на отправку содержимого ленда во внешнюю модель на сейчас нет.

Старт только после окончания статической фазы и только если нет `failed` или пользователь явно разрешил ИИ несмотря на них. Без `failed` дополнительного вопроса нет.

Вход одним контекстом: файлы ленда, HTML и текст, скриншоты, живой временный URL, `languages[]` и `countries[]` из строки каталога до скачивания. Если в админ-конфиге заданы ожидаемые языки поверх метаданных, использовать их по правилу конфига. Режим «замена или дополнение» исходным ТЗ не задан.

ИИ ищет дефекты и только перечисляет их. Он не блокирует ленд и не ставит общий статус.

Текст: орфография; смешение языков; смысл отдельных фраз; личные имена, нетипичные для ГЕО; валюта, не соответствующая ГЕО.

Картинки: повтор там, где макет требует уникальное изображение. Примеры: одно и то же фото у разных комментаторов; одно и то же фото повторено в основном контенте.

В отчёт принимается только находка, у которой есть все три части: путь к файлу, цитата текста, скриншот. Иначе находки в блоке нет.

Статусы блока ИИ из исходного ТЗ:

| Статус | Когда |
|--------|--------|
| Список готов | Прогон завершился, в блоке только полные доказательства |
| не запускался (ждут решения пользователя) | Есть `failed`, человек ещё не ответил |
| ошибка после повторов | Часть ИИ упала после 3 повторов. Статика остаётся |

Отдельного статуса «пользователь отказался» в исходном ТЗ нет. Факт отказа хранить как решение человека, не как вердикт ленда. См. предлагаемый контракт и открытые вопросы.

Затраты брать только из ответа провайдера. Свой тариф не считать. Если учёта в ответе нет, статистика ТЛ — состояние «учёта нет», не нули. QA затраты не получает.

Lighthouse ИИ не блокирует и не заменяет.

## Lighthouse

Эталон запуска: `src/steps/07-lighthouse.js`. Два прогона: `mobile` и `desktop`. Категория только `performance`. Accessibility не добавлять.

В сводку входят: performance score, First Contentful Paint, Largest Contentful Paint, Total Blocking Time, Cumulative Layout Shift, Speed Index, Time to Interactive. Для обоих прогонов.

Своего порога «пройдено / не пройдено» нет. Поле вердикта по баллу не создавать.

Статус блока: выполнен или ошибка прогона. Это не оценка ленда. В таблице раздела 9 для ошибки сказано «ошибка после повторов».

Доказательство: сводка метрик обоих прогонов. Временный подписанный URL в постоянный отчёт не класть.

Ошибка Lighthouse не стирает статику и ИИ.

Повторы: раздел 10 не называет Lighthouse в списке частей «скачивание, распаковка, статика, развёртывание, ИИ». Раздел 9 говорит «ошибка после повторов». Критерий приёмки 7 говорит «ошибка Lighthouse после 3 повторов». Для Lighthouse фиксируем те же 3 автоповтора со ссылкой на критерий 7. После них — ошибка этой части, успешные блоки не удалять.

## Отчёт, сравнение, хранение

Одна страница из трёх блоков: статика, ИИ, Lighthouse. Общего статуса страницы нет. Статусы частей независимы.

Хранение 3 месяца. Сравнение: отдать прошлый отчёт того же `human_id` рядом по данным, без вычисленного вердикта сравнения. Если прошлого нет, отдать пусто, не синтетический итог.

Постоянный отчёт не содержит токен, подписанный URL скачивания и временный URL стенда. Образец `preview_image` в постоянный отчёт не класть. `name` в отчёте есть.

Язык текстов отчёта, которые пишет система, — русский. Цитаты ленда не переводить.

## Ошибки и повторы

Для сбоя скачивания, распаковки, статической проверки, развёртывания и ИИ: автоматический повтор 3 раза, затем ошибка этой части. Для Lighthouse — тоже 3, по критерию 7.

Повтор относится к упавшей части. Успешный блок не отбрасывать.

Пользователь видит, на каком шаге ошибка, без общего «ленд плохой». В данных ответа нет поля общего вердикта.

Что считать одной попыткой опроса уведомлений, исходное ТЗ не задаёт.

## Админ-конфиг

Владелец — ТЛ. История изменений не ведётся.

В конфиге только то, что уже есть в правилах и что ТЛ может поменять без релиза: списки разрешённых внешних префиксов, списки запрещённых макросов и скриптовых признаков, пороги размеров изображений, CSS и встроенного скрипта, флаг `expectFormMacro`, ожидаемые языки, если их нужно переопределить поверх метаданных ленда.

Стартовое наполнение — раздел статики и `expectFormMacro: true`. Новые проверки и новые числа не добавлять. Менять можно только уже существующие параметры.

Стартовые пороги и префиксы — таблица статики выше. Списки, которые в таблице закрыты словами «как в модуле», брать из поведения названных файлов, не дополнять новыми признаками.

## Оркестрация

1. Найти строку в кэше последних 300. Если передан `uuid`, взять строку с парой `human_id` и `uuid`, даже при повторе `human_id`. Пара не совпала — стоп, без скачивания. Если `uuid` нет, найти точный `human_id`. При промахе — одно обновление и повтор поиска. Несколько строк без `uuid` или отсутствие — стоп, без скачивания.
2. Сохранить метаданные карточки.
3. `Download Requested`, затем уведомление `lander.download` / `done` / тот же `lander_uuid`, затем файл `kind=original`.
4. Удалить предыдущий каталог этого пользователя. Распаковать. Чужой каталог не трогать.
5. Статика. Структура `failed` — остальные пункты не запускать.
6. Если есть `failed` — ждать явное решение по ИИ. Если нет — идти дальше без вопроса.
7. На продолжении: стенд, затем ИИ. Lighthouse по временному URL стенда, не блокирует ИИ.
8. Когда отчёт полностью создан, распакованный каталог можно удалить. Запись отчёта остаётся.
9. По запросу отдать прошлый отчёт того же `human_id`. Вердикт сравнения не считать.

Разные пользователи идут независимо. Не больше одного развёрнутого ленда на пользователя.

## Предлагаемый контракт MVP

Имена ниже — предложение для связи с frontend. Исходное ТЗ их не фиксирует. Бизнес-правила остаются в разделах выше. Если формулировка здесь расходится с ними, верны разделы выше.

QA на чужие отчёты, `GET /admin/rules`, `PUT /admin/rules`, `GET /admin/costs`, `GET /admin/users` и `POST /admin/users` получает отказ. Пустые чужие данные, нулевые затраты и список пользователей вместо отказа не отдавать.

`POST /session`. Тело `{ "login", "password" }`. Сначала сравнение пары с `TL_LOGIN` и `TL_PASSWORD`: совпала — роль ТЛ. Иначе пользователь из Neon, роль из записи. Чужой логин или пароль — отказ входа, без уточнения, какое из двух неверно. Пароль в ответ и в логи не писать. Восстановления пароля и самостоятельной смены пароля нет.

|-----|----------------|-----|------------|
| `POST /session` | `POST /session` | оба | Вход. Тело `{ "login", "password" }`. Сначала пара `TL_LOGIN` / `TL_PASSWORD` (роль ТЛ), иначе пользователь из Neon. В ответе роль `ТЛ` или `QA`. Чужой логин или пароль — отказ без уточнения |
| `GET /session` | `GET /session` | оба | Текущая роль |

| `POST /admin/users` | `POST /admin/users` | только ТЛ | Тело: `login`, `password`, `role` (`ТЛ` или `QA`). Создать пользователя в Neon |

`GET /catalog` отдаёт элементы кэша для таблицы экрана и не ходит в AIO сам по себе: кэш наполняет запрос п. 4.1. Порядок элементов — числовой `human_id` по убыванию. Клиент этот порядок не пересчитывает. Поиск по подстроке этот метод не выполняет.

`POST /checks` с одним `human_id` не создаёт проверку и не скачивает файл, если ленда нет среди 300 или строк с этим `human_id` несколько. В коллизии отдать строки карточки без выбора победителя. `POST /checks` с `human_id` и `uuid` берёт строку кэша, у которой совпали оба поля, даже если `human_id` повторяется. Если такой пары в кэше нет — ошибка, скачивание не начинается. `preview_image` в ответе до скачивания допустим как контекст. В `GET /reports/{report_id}` образец `preview_image` не класть.

Предлагаемые шаги `GET /checks/{check_id}`: `catalog`, `download_request`, `notifications`, `download_file`, `unpack`, `static`, `ai_gate`, `stand`, `ai`, `lighthouse`, `report`.

Предлагаемые состояния шага: `pending`, `running`, `retrying`, `waiting_user`, `done`, `failed`, `skipped`. Это состояния хода, не статусы пункта `passed` / `warning` / `failed` и не вердикт ленда.

Поле `replaced_previous_stand: true`, если этому пользователю снесли предыдущий каталог. Чужой каталог из-за этого флага не меняется.

`stand_url` отдавать только в ходе живого просмотра. В объект постоянного отчёта не писать. В логи не писать.

`ai-decision` принимать только когда статика уже есть и в ней есть `failed`, а ИИ ещё не стартовал. `deny` не ставит общий статус. Как подписать блок ИИ после `deny`, см. открытый вопрос: код решения хранить отдельно от трёх статусов раздела 9.

`GET /admin/costs`: если провайдер вернул учёт — отдать эти цифры без тарифа продукта. Если нет — `{ "usage_reported": false }` и без выдуманных сумм. Схему полей провайдера исходное ТЗ не задаёт: лишние ключи не достраивать.

`PUT /admin/rules` принимает только существующие параметры. Неизвестная проверка и новое число, которого не было в правилах, не сохраняются.

`POST /admin/users` пишет в Neon логин, хеш пароля и роль. Открытый текст пароля не хранить. Пароль из `TL_PASSWORD` в базу не копировать. Других полей учётки не добавлять. Логин, совпавший с `TL_LOGIN` или с уже существующим логином, не создавать. Методов удаления и правки пользователя нет.

`GET /admin/users` отдаёт логин и роль. Пароль и хеш не отдавать. Учётку `TL_LOGIN` включить в список и пометить как заданную окружением, без пароля. QA на оба метода получает отказ.

## Критерии приёмки

Принимает заказчик. Золотого набора лендов нет. Пороги баллов Lighthouse в приёмку не входят.

| # | Готово, если |
|---|----------------|
| 1 | QA не получает чужие отчёты и затраты ни через один метод. ТЛ получает все отчёты и затраты, когда провайдер вернул учёт. Роли — учётки помощника. QA не создаёт пользователей и на `GET /admin/users` и `POST /admin/users` получает отказ. ТЛ из окружения входит и может создать пользователя с ролью |
