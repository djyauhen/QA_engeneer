## 1. Назначение и границы MVP

Внутренний инструмент для команды до 10 человек. Пользователь выбирает ленд в каталоге или вводит `human_id`, система скачивает архив, прогоняет статические проверки, поднимает изолированный просмотр, вызывает ИИ и Lighthouse и показывает отчёт. Отчёт рекомендательный. Общего вердикта «годен / не годен» нет. Решение принимает человек.

**Входит в MVP**

| Шаг | Результат |
|-----|-----------|
| Таблица каталога, выбор строки или ввод `human_id` | Карточка ленда и запуск проверки |
| Скачивание zip из AIO | Архив `original` («Original upload») |
| Статический разбор | Пункты правил SpyOwl со своим статусом |
| Стенд и ИИ | Просмотр с макросами и список дефектов |
| Lighthouse | Сводка mobile и desktop, без порога балла |
| Отчёт | Одна страница, хранение 3 месяца, сравнение с прошлым отчётом того же `human_id` |

**Не входит**

- Общий статус проверки и автоматический блок ленда.
- Отдельный логин каждого QA в AIO. Один сервисный токен.
- Анализ архива `merged` (см. правило в разделе 4).
- Исходящие интеграции: Jira, Telegram, почта, таблицы.
- Отдельное скрытие персональных данных на ленде: таких данных не ожидается.
- История изменений админ-конфига.
- Фиксированный суточный объём проверок.
- Золотой набор эталонных лендов. Приёмку делает заказчик системы.
- Саморегистрация.
- Восстановление пароля и самостоятельная смена пароля.
- Удаление и редактирование пользователей.

## 2. Роли и права

| Роль | Кто | Что может |
|------|-----|-----------|
| ТЛ | Максимальный доступ | Запуск всех проверок. Все отчёты всех пользователей. Статистика затрат на модели. Админ-конфиг правил. Создание пользователей помощника. Список пользователей: логин и роль. |
| QA | Ниже ТЛ | Запуск полного набора проверок. Только свои отчёты. Статистики затрат нет. Конфиг правил не меняет. Пользователей не создаёт. Экрана пользователей нет. |

Создавать пользователей может только ТЛ. QA этого экрана и метода не видит и не вызывает. Саморегистрации нет.

Первый ТЛ не создаётся через интерфейс. Его логин и пароль задаются в `.env`: `TL_LOGIN` и `TL_PASSWORD`. Значения в репозиторий, отчёт и логи не писать. Это не учётка AIO и не `AIO_TOKEN`.

Остальных пользователей создаёт ТЛ в продукте. У создаваемого: логин, пароль, роль ТЛ или QA. Запись в Neon. Пароль созданного пользователя в базе только как хеш, не открытым текстом. Пароль из `TL_PASSWORD` в базу не копировать. Поля записи — логин, хеш пароля и роль. Других полей учётки не добавлять.

Вход — предлагаемый `POST /session`. Тело: `{ "login", "password" }`. Сначала сравнение пары с `TL_LOGIN` и `TL_PASSWORD`: совпала — роль ТЛ. Иначе пользователи из Neon. Чужой логин или пароль — отказ входа, без уточнения, какое из двух неверно. Восстановления пароля и самостоятельной смены пароля в MVP нет.

Создание — предлагаемый `POST /admin/users`, только ТЛ. Тело: логин, пароль, роль (`ТЛ` или `QA`). Логин, совпавший с `TL_LOGIN` или с уже существующим, не создавать. QA на этот метод получает отказ. Список для ТЛ — предлагаемый `GET /admin/users`: логин и роль, без пароля и без хеша. Учётку из окружения в этом списке пометить как заданную окружением, без пароля. Удаления и редактирования пользователей в MVP нет. Имена маршрутов предлагаемые.

Учётные записи помощника — не учётные записи AIO.

## 3. Пользовательский сценарий

1. Пользователь открывает экран запуска и видит таблицу лендов из каталога последних 300. Это тот же кэш, который наполняется запросом `POST /api/v1/tables/data`. Запрос в AIO не меняется: `sort_key` `_identity`, `sort_direction` `desc`, `filters` пустой, `dates` не передаётся. Колонки ровно три, по порядку: `human_id` с заголовком «id», `name` с заголовком «Лендинг», `created_at` с заголовком «Создано». Других колонок нет. `uuid` в колонку не выводится. `created_at` берётся с верхнего уровня строки каталога, не из `_identity.created_at`. Если поля нет, ячейка пустая, строку не выбрасывать. Сортировка таблицы — по убыванию числового значения `human_id` (больший id сверху), не лексикографическая сортировка строк. Её делает сервер в ответе списка для экрана. Клиент показывает порядок ответа и сам его не пересчитывает.
2. Поле поиска фильтрует уже показанную таблицу по подстроке в `human_id` или `name`, без учёта регистра. Поиск не ходит в AIO и не подменяет каталог. Пустое поле — вся таблица. Кнопка «Обновить» обновляет каталог сразу.
3. Запуск проверки. Выбор строки запускает проверку этой строки: на сервер уходят `human_id` и `uuid` этой строки. Для явного выбора строки коллизия одинаковых `human_id` так снимается. Запуск только текстом `human_id`, без выбранной строки, по-прежнему сравнивает `human_id` как точную строку (пример формата: `359226`). Ровно одна строка — запуск как раньше. Несколько строк — выбор не делается, скачивание не начинается, показана коллизия. Нет среди последних 300 — прежнее сообщение, скачивание не начинается. Промах кэша по-прежнему: одно обновление и повтор поиска.
4. До скачивания система сохраняет метаданные найденной строки: `uuid`, `name`, `human_id`, `countries[]`, `languages[]`, `lander_type.name`, `status`, `preview_image`, `mvt_settings`. Карточка с этими полями остаётся на экране. Таблица её не заменяет. Текст оффера из примера в правила не входит.
5. Система запрашивает выгрузку, опрашивает уведомления и скачивает zip `kind=original`.
6. Распаковка. Если у этого пользователя уже был развёрнутый каталог, он удаляется. Одновременно у пользователя один ленд.
7. Статические проверки. Пункты, которые не зависят от провала структуры, можно выполнять параллельно друг другу.
8. Если есть критичные статические находки, ИИ сам не стартует. Пользователь видит статический результат и явно разрешает или не разрешает ИИ.
9. Если критичных находок нет, либо пользователь разрешил продолжить: стенд, затем ИИ. Lighthouse идёт по временному URL стенда и не блокирует ИИ и не заменяет его.
10. После того как отчёт полностью создан, распакованный каталог можно удалить. Запись отчёта остаётся.
11. Пользователь читает отчёт и сам решает, принимать ленд или нет. Может открыть прошлый отчёт того же `human_id` и сравнить с текущим.

Разные пользователи проверяются независимо. У каждого не больше одного развёрнутого ленда.

Язык интерфейса и отчёта — русский. Текст ленда может быть на любом языке.

## 4. Входные данные и контракт AIO

### Идентификация

Пользователь запускает проверку выбором строки или точным `human_id`. `uuid` в поле ввода не набирается и в колонку таблицы не выводится. При выборе строки `uuid` этой строки уходит на сервер вместе с `human_id`.

Поля карточки ленда, которые нужны до скачивания:

| Поле | Зачем |
|------|--------|
| `uuid` | Аргумент скачивания и сопоставление уведомления |
| `human_id` | Ключ отчётов и сравнения |
| `name` | Подпись в отчёте |
| `countries[]` | Ожидаемое ГЕО для ИИ |
| `languages[]` | Ожидаемые языки для ИИ |
| `lander_type.name` | Тип, пример значения: `Preland w/ Form` |
| `status` | Контекст, не вердикт помощника |
| `preview_image` | Контекст, не замена скриншота стенда |
| `mvt_settings` | Контекст вариантов, в правила статики не превращать |

**Каталог последних 300**

Система хранит последние 300 лендов. Сортировка запроса в AIO — сначала новые. Если список постраничный, страницы собираются, пока не будет 300 записей или список не кончится.

Фоновое обновление — каждые 10 минут. Кнопка «Обновить» запрашивает список сразу. Опрос раз в 10 минут только наполняет кэш, чтобы ввод `human_id` не ждал сеть.

`human_id` сравнивается как точная строка (пример: `359226`). Если его нет в кэше, список обновляется один раз, затем поиск повторяется. Если после этого обновления записи нет, проверка останавливается с ясным сообщением: ленд не среди последних 300. К скачиванию не переходим.

Если несколько строк с одним `human_id` и запуск идёт только текстом `human_id`, без `uuid` выбранной строки, выбор не делается: проверка останавливается и показывает коллизию. Если вместе с `human_id` передан `uuid` выбранной строки и эта пара есть в кэше, берётся эта строка. Пара не совпала — ошибка, скачивание не начинается.

Экран запуска показывает кэш таблицей с тремя колонками («id», «Лендинг», «Создано») и сортировкой по числовому `human_id` по убыванию. Порядок запроса в AIO остаётся «сначала новые».

Карточка читается из `_identity` строки списка (п. 4.1). В захвате у каждой из 50 строк там есть `uuid`, `human_id`, `name`, `countries`, `languages`, `mode`, `lander_type`, `lander_template`, `preview_image`, `status`, `mvt_settings`. `human_id` на верхнем уровне строки нет: он только внутри `_identity`. Верхний `uuid` строки в этом ответе совпадает с `_identity.uuid`. `status` — строка (в захвате у всех строк `Fine`). `mvt_settings` — строка с JSON, не объект. Нет поля в строке — сохраняем пустым и идём дальше. Обязательны `uuid` и `human_id`.

`Content-Type: application/json`

`filters` и `dates` в снимке — состояние экрана таблицы: режим `Editor` и октябрь 2026, пояс `Europe/Minsk`. Каталог последних 300 эти значения не закрепляет. В запросах каталога `filters` — пустой массив, ключ `dates` не передаётся. Остальные поля тела остаются как в захвате. `page` начинается с 1 и растёт на 1. `limit` остаётся 50. `search` — пустая строка. `sort_key` `_identity` и `sort_direction` `desc` задают порядок «сначала новые».

### Авторизация AIO

Один сервисный токен в окружении (`AIO_TOKEN`). На URL каждого вызова AIO из этого раздела ставится query-параметр `token`: список `POST /api/v1/tables/data`, `POST /api/v1/actions/process`, опрос уведомлений, скачивание. Cookie нет. Заголовка `Authorization` нет. Заголовка `x-tenant-id` нет. В репозиторий, в отчёт и в логи значение токена не писать.

### Запрос скачивания

`POST https://app.aio.tech/api/v1/actions/process`  
`multipart/form-data`:

| Поле | Значение |
|------|----------|
| `action` | `Lander\Download` |
| `repository` | `Eloquent\LanderRepository` |
| `arguments[is_archived]` | `true` |
| `uuids[0]` | `uuid` ленда |

Ответ `200`: `messages[].message` = `Download Requested`; `primary` и `uuid` повторяют `uuid` ленда. Файла в этом ответе нет.

### Опрос уведомлений

`GET https://app.aio.tech/api/v1/notifications?limit=25&page=1&unread_only=false`

Ищем элемент с `notification.type` = `lander.download`, у которого `payload.lander_uuid` равен запрошенному `uuid` и `payload.status` = `done`.

В `payload` также есть `human_id`, `lander_name`, `lander_uuid`, `link_ttl_days` (в наблюдаемом ответе срок ссылки 7 дней). `payload.files[]`:

| `kind` | `label` | Смысл |
|--------|---------|--------|
| `merged` | Merged export | Ленд с текущими изменениями AIO |
| `original` | Original upload | Архив, которым ленд когда-то загрузили |

### Какой zip берём

**Правило:** в MVP берём только `kind=original` («Original upload»). `merged` не скачиваем и не проверяем.

`POST /api/v1/actions/process` по-прежнему отвечает только `Download Requested`. Это не адрес файла. Затем опрос уведомлений, как выше. Из `payload.files[]` выбирается файл с `kind=original`.

Original — архив, которым ленд загрузили, без текущих правок AIO. Проверки статических макросов (`{{form}}`, `{{cdn}}/`, защита трекера) могут дать `failed`, если эти макросы есть только в выгрузке merged. Это ожидаемо и не повод вернуться к merged.

Дальше файл берётся по URL из уведомления. URL подписанный и ограничен по времени. Образцы URL не хранить. Ссылка не является результатом проверки.

### Архив

Ожидаемая основа: в корне `index.html` или `index.php`, каталоги `css`, `js`, `images`. Типы preland, land и offer этой раскладке соответствуют. Отличие типов — наличие формы (скрипт или макрос), а не другая раскладка папок.

Образец `docs/multy_th_kov_ek_yod-chinsupakul_thethaiger_en_-templ1-_250-_-.zip`, верхний уровень (104 записи внутри): `index.html`, `favicon.ico`, каталоги `css/`, `js/`, `images/`, `fonts/`. Правила структуры шире этого образца и заданы проверкой SpyOwl, а не списком папок образца.

## 6. Стенд, макросы, изоляция, очистка

Стенд нужен, чтобы человек и ИИ видели ленд с подставленными макросами.

Подстановка при отдаче страницы — как у Compilator, `vendor/compilator/server.mjs`:

| Макрос | Чем заменяется |
|--------|----------------|
| `{{form}}` | HTML из конфига стенда `form.html` |
| `{{aio.visit.fields.offer_name.for_visitors}}` | Строка `brand_name` из конфига стенда `config.json` |
| `{{cdn}}` | База CDN стенда; в страницу также передаётся `window.__CDN_BASE__` |

Другие макросы этот просмотр не подставляет. Пайплайн SpyOwl `src/steps/04-macros.js` заменяет только `{КЛЮЧ}` из `macros.conf` и к просмотру AIO-ленда не относится. Значения-примеры из `macros.conf` в продукт не переносить.

Пользователь получает временный URL, если окружение умеет его выдать.

Пока QA явно не разрешил действия ленда, развёрнутая копия сама ничего не выполняет: нет отправки лидов и нет срабатывания сторонних пикселей. Разрешение — явное действие QA на этом просмотре, не молчаливое включение.

Очистка:

- Новый запуск того же пользователя удаляет его предыдущий распакованный каталог до развёртывания нового.
- После полного создания отчёта каталог можно удалить.
- Отчёты не удаляются вместе с каталогом.
- У пользователя не больше одного развёрнутого ленда. Пользователи друг друга не вытесняют.

## 7. ИИ-проверка

ИИ стартует только после окончания статической фазы и только если нет критичных статических находок или пользователь явно разрешил ИИ несмотря на них.

Модель: Qwen, быстрый вариант. Цель всего пути от ввода `human_id` до отчёта — 2–3 минуты. Ограничения компании на отправку содержимого ленда во внешнюю модель на сейчас нет.

Вход модели вместе, одним контекстом проверки: файлы ленда, HTML и текст, скриншоты, живой временный URL.

Ожидаемые языки — `languages[]`, ожидаемые страны — `countries[]` из строки каталога, полученной до скачивания.

ИИ ищет дефекты и только перечисляет их. Он не блокирует ленд и не ставит общий статус.

Текст:

- орфография;
- смешение языков;
- смысл отдельных фраз;
- личные имена, нетипичные для ГЕО;
- валюта, не соответствующая ГЕО.

Картинки: повтор там, где макет требует уникальное изображение. Примеры: одно и то же фото у разных комментаторов; одно и то же фото повторено в основном контенте.

Доказательство каждой находки ИИ обязательно: путь к файлу, цитата текста, скриншот. Находка без этих трёх частей в отчёт ИИ не принимается.

## 8. Lighthouse

Отдельный блок отчёта. Роль рекомендательная. Своего числового порога «пройдено / не пройдено» нет: баллы показываем, ленд по ним не режем.

Категорию accessibility этот шаг не считает; отдельный прогон accessibility в MVP не добавлять.

Статус блока Lighthouse: выполнен или ошибка прогона. Это не оценка ленда.

Доказательство: сводка результата (метрики обоих прогонов). Образец URL стенда в постоянный отчёт не класть, если URL временный и подписанный.

## 9. Отчёт, статусы, сравнение, хранение, затраты

Одна страница. Три блока:

1. Статика — пункты из раздела 5, каждый со своим статусом.
2. ИИ — список дефектов с доказательствами, отдельным блоком.
3. Lighthouse — сводка из раздела 8.

Общего статуса страницы нет. Статусы частей независимы:

| Часть | Статусы |
|-------|---------|
| Статика (структура, размеры, скрипты и остальные пункты раздела 5) | Сводка по пунктам: есть `failed` / только `warning` / все `passed`. Плюс отдельное состояние «проверка не завершилась» при ошибке прогона. |
| ИИ | Список готов / не запускался (ждут решения пользователя) / ошибка после повторов. |
| Lighthouse | Выполнен / ошибка после повторов. |

Если статика посчиталась, а ИИ после повторов упал, статический блок сохраняется, у ИИ статус ошибки. То же для Lighthouse: его ошибка не стирает статику и ИИ.

Хранение отчёта — 3 месяца. Пользователь открывает прошлый отчёт того же `human_id` и видит его рядом с текущим. Общий вердикт сравнения не вычисляется.

ТЛ видит все отчёты и статистику затрат на модели. QA видит только свои отчёты и не видит затраты. Цифры затрат берутся из ответа провайдера модели. Свой тариф не выдумывать.

## 10. Ошибки и повторы

Для сбоя скачивания, распаковки, статической проверки, развёртывания и ИИ: автоматический повтор 3 раза, затем ошибка этой части.

Повтор относится к упавшей части. Успешный статический результат при последующем падении ИИ не отбрасывается. То же для уже полученного блока Lighthouse.

Пользователь видит, на каком шаге ошибка, без общего «ленд плохой».

## 14. Критерии приёмки MVP

Принимает заказчик системы. Золотого набора лендов нет. Пороги баллов Lighthouse в приёмку не входят.

1. QA и ТЛ входят в помощник под своими ролями. QA не видит чужие отчёты и не видит затраты. ТЛ видит все отчёты и блок затрат, если провайдер модели вернул учёт использования. QA не создаёт пользователей; ТЛ из окружения входит и может создать пользователя с ролью.
2. Запуск ленда из последних 300 — выбором строки (`human_id` и `uuid` этой строки) или вводом одного точного `human_id` — приводит к скачиванию `original` после `Download Requested` и уведомления `lander.download` со `status=done` и тем же `lander_uuid`. Список для этих 300 — `POST /api/v1/tables/data`, п. 4.1. Экран показывает этот кэш таблицей; порядок таблицы — числовой `human_id` по убыванию и запрос в AIO не меняет. Ответ `process` без файла сам по себе отчётом не считается. `human_id` вне последних 300 скачивание не запускает. Ввод только `human_id` при нескольких строках скачивание не запускает.
3. В отчёте есть все пункты раздела 5, которые запустились. При заведомо битой структуре остальные пункты отсутствуют, ИИ сам не вызывается, пользователь может явно разрешить ИИ.
4. При статике без `failed` ИИ вызывается без дополнительного вопроса. В блоке ИИ у каждой находки есть путь, цитата и скриншот, общего статуса нет.
5. Стенд открывается по временному URL, макросы из раздела 6 подставлены. До явного разрешения QA ленд не отправляет лид и не дергает сторонние пиксели.
6. Повторный запуск того же пользователя убирает предыдущий каталог. Второй пользователь в это время может держать свой ленд.
7. Блок Lighthouse показывает сводку mobile и desktop без вердикта по баллу. Ошибка Lighthouse после 3 повторов не удаляет статику.
8. Сбой ИИ после 3 повторов оставляет статику на месте и помечает ИИ ошибкой.
9. Отчёт на русском, без единого общего статуса. Прошлый отчёт того же `human_id` открывается рядом с текущим.
10. В репозитории, отчёте и логах нет значения токена и подписанных URL.
11. Кнопка «Обновить» обновляет каталог, не дожидаясь 10 минут.
